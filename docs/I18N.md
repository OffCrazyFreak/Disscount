# Internationalisation

Disscount ships in Croatian (`hr`, the source and default), English (`en`), Italian (`it`), Slovenian (`sl`) and German (`de`). The frontend uses next-intl with ICU messages, the backend uses Spring's `MessageSource`, and the transactional emails reuse the frontend catalogs. Legal pages (privacy, terms, data deletion, licence) are Croatian only for now and get translated once their rewrite is done.

## URLs and routing

Every page lives under `src/app/[locale]/`. Croatian keeps its unprefixed URLs (`/products`), the other languages get a prefix (`/en/products`), which is next-intl's `as-needed` mode configured in `src/i18n/routing.ts`. A prefixed Croatian URL such as `/hr/products` redirects to the unprefixed one.

There is no redirect by `Accept-Language`. Google advises against it, and a shared link should open in the language it was shared in. Instead, `locale-suggestion.tsx` shows a small banner offering the saved language when the page language differs from it.

The one exception is a bare `/`: `src/proxy.ts` sends it to `/<locale>` when the `NEXT_LOCALE` cookie holds a non-Croatian choice, so typing the domain or launching the installed app lands in the language you picked. Crawlers never carry the cookie.

Two gaps follow from this. App shortcuts in the installed app point at unprefixed paths, so they open in Croatian, because a site has one static manifest. And an installed app launched offline lands on the Croatian offline page, since the redirect needs the network.

Root params are on in Next.js 16.3 and later, so `src/i18n/request.ts` reads the locale with `rootParams.locale()` and pages need no `setRequestLocale` call. Route handlers cannot read root params and pass the locale explicitly, which is why the OG image routes take it from their own `params`.

## Where the language is stored

- **The URL** decides what a page renders. Nothing else does.
- **The `NEXT_LOCALE` cookie** is written only when someone picks a language in the switcher, never on a plain visit. That keeps it inside the ePrivacy exemption for user-interface customisation, so it needs no consent. next-intl's own cookie is turned off (`localeCookie: false`) because it would be written on every visit.
- **The account** stores the choice in the better-auth `user.locale` column (migration `0002_user_locale`), validated by a `z.enum(LOCALES)` validator on the field, so `update-user` rejects anything else. On sign-in the account wins and overwrites the cookie; an account with no language yet takes the saved cookie, or the page language when there is none (`locale-sync.tsx`). Emails use this column.

The switcher sits in the header on desktop, the sidebar footer on mobile, the page footer, and Settings > Preferences. The settings picker is left out of onboarding, which reuses the Preferences tab, and is locked while the settings form has unsaved changes, because switching remounts the tree under the new `[locale]` segment and would drop them.

## Message catalogs

Messages live in `frontend/src/i18n/messages/<locale>/<namespace>.json`, one file per namespace, registered in each locale's `index.ts`. Croatian is the source: every key exists there first, and `AppConfig` in `src/typings/next-intl.d.ts` types `t()` keys against the Croatian catalog, so a typo is a type error.

`load-messages.ts` merges each translation over Croatian, so a missing key shows Croatian text instead of a raw key. That is a safety net only: CI runs `pnpm i18n:check` (`scripts/check-i18n.mjs`), which fails on missing or extra keys, invalid ICU, arguments or tags that differ from Croatian, and plural branches that do not match the language's CLDR categories. `--allow-missing` reports untranslated keys without failing, for use while translating.

To add a namespace, run `node scripts/i18n-add-namespace.mjs <name>`. It creates the empty file in every locale and registers it in each `index.ts`.

Each page currently sends the whole catalog for its locale to the client (about 67 KB raw). Splitting it per route is possible with `NextIntlClientProvider`'s `messages` prop, but has not been worth the bookkeeping yet.

## Writing messages

- Use ICU for anything that varies: `{count, plural, one {...} few {...} other {...}}` for counts, `{amount, number, ::currency/EUR}` for money, rich text tags like `<link>...</link>` for inline markup. Never concatenate translated fragments.
- Croatian plurals need `one`, `few` and `other`; Slovenian adds `two`. The check script enforces this.
- Data constants (navigation items, feature lists, FAQ entries) hold message keys (`labelKey`, `descriptionKey`) or ids, not text, and the component calls `t()`.
- Import `Link`, `redirect`, `useRouter` and `usePathname` from `@/i18n/navigation`, not from `next/link` or `next/navigation`, so links keep the current locale.
- `eslint-plugin-i18next`'s `no-literal-string` rule flags JSX text and text-carrying attributes (`aria-label`, `alt`, `title`, `placeholder`, `*Label`, `*Title` and similar) that are not translated.

## Tone

Every language uses the informal singular address (`ti`, `you`, `tu`, `du`) and ungendered forms, because the app aims to sound personal. In Slovenian, Italian and Croatian that often means avoiding past participles and conditionals that agree with the reader's gender, by using the present tense, an impersonal form or a noun. The company speaks as "we". Each language keeps its usual names for system UI (iOS and Chrome menu labels) so install instructions match what people see.

## Formatting

Dates, numbers and prices go through the helpers in `src/utils/` (`formatPrice`, `formatDate`, `formatRelativeTime` and the rest), which take the locale as a required argument. `src/i18n/formatting.ts` maps app locales to `Intl` locales (English uses `en-GB`) and pins the time zone to `Europe/Zagreb`, so server and client render the same date.

## Forms and validation

zod schemas carry message keys (`validation.required`) rather than text. `FormMessage` and `FieldError` translate them through `useValidationMessage`, which passes anything that is not a known key through unchanged. `zod-locale.tsx` switches zod's built-in messages to the current locale on the client.

## Backend

The backend resolves error and validation messages from `backend/src/main/resources/messages*.properties` using the request's `Accept-Language`, which the frontend's API client sets from `<html lang>`. Croatian is the default (`spring.web.locale=hr`), and `fallback-to-system-locale=false` keeps the server's own locale out of it. Services throw message codes such as `error.shoppingList.notFound`, `GlobalExceptionHandler` resolves them, and bean validation annotations use `{validation.*}` codes. Every key needs an entry in all five files.

## Emails

The react-email templates build their text with next-intl's `createTranslator` from the `emails` namespace (`src/lib/email/email-copy.ts`), in the locale stored on the user. The reset link lifetime in the copy comes from `RESET_TOKEN_TTL_SECONDS`, so the text cannot drift from the real expiry.

Run the `email` package script for the preview server. The entries in `src/emails/` are preview-only and take their `PreviewProps` from the catalogs through `src/emails/_preview/preview-props.ts`; change `PREVIEW_LOCALE` there to preview every email in another language. The send path imports the templates from `src/emails/_templates/`, so the preview catalogs never load in production.

## SEO

`generateMetadata` in each page sets the canonical URL and `hreflang` alternates for all five languages plus `x-default` (Croatian) through `pageAlternates` in `src/i18n/alternates.ts`. The sitemap lists every page once with the same alternates, and `robots.ts` repeats each disallow rule per locale prefix. OG and Twitter images are rendered per locale by `src/app/og/localized-og.tsx`.

The web app manifest stays Croatian: a site has one manifest, and its `lang` is `hr`.

## Known trade-offs

- An unknown URL returns status 200 with `noindex` rather than a real 404, because `[locale]/loading.tsx` starts streaming before the `[...rest]` catch-all can call `notFound()`. Search engines treat it as a soft 404.
- The full catalog ships to the client, as described under Message catalogs.
